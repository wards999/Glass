# 0001 — Repo layout, core FFI, and Mac build system

**Status:** accepted (M0)

## Context
`core` (Rust) must be shared by the Rust Windows app and the Swift macOS app, and
CI has to build all three on GitHub runners.

## Decision
- One Cargo workspace at the repo root: `core`, `app-win`, `tools/*`.
- `core` builds as both `rlib` (for `app-win`) and `staticlib` (for `app-mac`).
- The C header `core/include/glass_core.h` is generated by cbindgen and **checked
  in**. CI regenerates it and fails if it differs, so the Swift side never builds
  against a stale ABI. `core` stays free of build dependencies.
- `app-mac` is a **SwiftPM package**, not an Xcode project. `CGlassCore` is a
  system-library target with a module map that includes the generated header and
  links `glass_core`. `Package.swift` points the linker at `../target/release`.
- Cargo's default (host) target is used on the macOS runner, which is Apple Silicon.

## Consequences
- `swift build` / `swift test` work headless in CI; no `.xcodeproj` to merge.
- When the app needs entitlements, an Info.plist and a signed `.app` bundle (Screen
  Recording/Accessibility prompts, M3b), add an Xcode project or a bundling step
  on top of the package. LATER(M3b).
- The developer must run `cargo build -p glass-core --release` before `swift build`.
- A universal (x86_64 + arm64) lib is not built; Apple Silicon only, per CLAUDE.md.
