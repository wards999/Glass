# M1 — Offline pipeline: results

**Status: DONE.** Both halves measured on real hardware with test build m1-test1.
**Date:** 2026-11-20 · **CI run:** 44643409364 (all green)

## What works
- **Windows host** (`glass record`): Windows.Graphics.Capture → GPU copy into an
  FFmpeg D3D11 frame pool → `hevc_nvenc` (p1/ull, zerolatency, delay 0, no
  B-frames, CBR 80 Mbps, ~1-frame VBV) → `.glsr`. No CPU copies of frames.
  4:2:0 (Main) and 4:4:4 (Rext) both work on the RTX 4070.
- **Mac client** (`GlassMac play`): `.glsr` parsed by core → length-prefixed
  conversion in core → `VTDecompressionSession` (hardware, real-time) →
  IOSurface-backed `420v`/`444v` pixel buffers → `CVMetalTextureCache` (zero
  copy) → YCbCr→RGB shader using the stream's colour matrix → `CAMetalLayer`,
  paced by `CADisplayLink` at capture timestamps. `--bench` decodes as fast as possible.
- **core**: `.glsr` format, Annex-B NAL and access-unit splitting, parameter sets,
  length-prefixed conversion, stats ring (p50/p99/stddev). 19 Rust unit tests.
- **Tests**: 6 XCTests in CI, covering fixture parse, 4:2:0 and 4:4:4 hardware
  decode, an offscreen Metal render check, and rejecting garbage. The Windows CI
  job round-trips the fixtures through `dump`/`pack`.

## Measured — Windows host (RTX 4070, Win11, 2560×1440 @ 165 Hz, 10 s, normal desktop activity)

**Test build m1-test1** (`record-clips.cmd`, run by the user with lots of on-screen motion):

| | encode p50 | encode p99 | encode max | avg bitrate | first IDR | frame p50 / p99 / max | frames (fps) |
|---|---|---|---|---|---|---|---|
| HEVC 4:2:0 | **2.43 ms** | **3.03 ms** | 12.09 ms | 52.9 Mbps | 75 KB | 55 / 68 / 160 KB | 1249 (124.9) |
| HEVC 4:4:4 | **3.21 ms** | **3.70 ms** | 23.73 ms | 54.4 Mbps | 73 KB | 55 / 86 / 211 KB | 1240 (124.0) |

WGC ts lead p50 2.79 / 3.12 ms. Capture interval p50 6.06 ms in both.

Earlier dev runs (mostly idle desktop, ~47 fps captured):

| | encode p50 | encode p99 | encode max | avg bitrate | first IDR | frame p50 / max | frames |
|---|---|---|---|---|---|---|---|
| HEVC 4:2:0 | 3.35 ms | 17.68 ms | 18.51 ms | 20.0 Mbps | 59 KB | 56 / 92 KB | 470 |
| HEVC 4:4:4 | 4.71 ms | 11.03 ms | 11.90 ms | 17.5 Mbps | 61 KB | 48 / 191 KB | 459 |

"Encode" = frame arrival in Glass → encoded packet out.

- **Target (SPEC §8) is 2–5 ms. Met at p50 and p99** for both 4:2:0 and 4:4:4
  under sustained motion. 4:4:4 costs about 0.8 ms more than 4:2:0.
- The high p99 in the idle dev runs went away once frames arrived steadily, which
  fits the "GPU/NVENC clocks drop between sparse frames" explanation. Single
  outliers remain (max 12–24 ms, probably the first frame or an IDR). Keep watching
  the idle→active case in M5 (e.g. keep the encoder warm).
- About 53 Mbps average for a busy 1440p desktop at 125 fps, under the 80 Mbps cap.
- **Capture interval** p50 6.06 ms (165 Hz) when the screen is changing. Gaps of
  hundreds of ms are idle periods, which is expected with only-on-change capture.
- **WGC timestamp:** `SystemRelativeTime` is *ahead* of arrival for about 98% of
  frames (p50 3.5 ms, max 7 ms). It's a present-target time, so Glass uses
  arrival as the capture timestamp (ADR 0002).

## Measured — Mac client

| | decode p50 | decode p99 | hardware | notes |
|---|---|---|---|---|
| CI VM, 320×192 fixture 4:2:0 | 1.01 ms | 7.37 ms | yes | 12 frames, first includes session warm-up |
| CI VM, 320×192 fixture 4:4:4 | 0.87 ms | 5.26 ms | **yes** | `444v` output, full-width chroma |
| **MacBook Air M4 (Mac16,12), 2560×1440 4:2:0** | **1.86 ms** | **2.13 ms** | yes | `420v`, max 3.41 ms, 515 fps bench (1249 frames) |
| **MacBook Air M4 (Mac16,12), 2560×1440 4:4:4** | **2.27 ms** | **2.46 ms** | **yes** | `444v`, max 3.69 ms, 415 fps bench (1240 frames) |

Real Mac: macOS 27.2.1, built-in display 2940×1912 @ 60 Hz, test build m1-test1.

Windowed playback (paced to capture timestamps on a 60 Hz display):

| | decode p50 / p99 | render+present p50 / p99 / max | present interval p50 / p99 | presented / superseded |
|---|---|---|---|---|
| 4:2:0 | 2.10 / 3.19 ms | 28.78 / 46.91 / 47.26 ms | 16.67 / 83.33 ms | 515 / 732 |
| 4:4:4 | 2.53 / 3.62 ms | 26.93 / 46.62 / 46.85 ms | 16.67 / 100.00 ms | 514 / 725 |

- **Decode meets SPEC §8 easily:** ~2 ms p50, under 2.5 ms p99 at 1440p, with the
  4:4:4 path only about 0.4 ms slower. **4:4:4 risk (SPEC §10) closed:** HEVC Rext
  4:4:4 decodes in hardware on the target Mac, IOSurface-backed `444v`.
- **render+present is the big number (~27–29 ms p50).** It's measured from
  command-buffer submit to `presentedTime` (photons). At 60 Hz that is roughly
  1.5–2 refreshes of queueing in `CAMetalLayer` (default 3 drawables, display sync
  on, playback not aligned to vsync). That's M5's job (display-linked presentation,
  `maximumDrawableCount = 2`, presenting just ahead of vsync). Re-measure there.
- "Superseded" is expected: a 125 fps source on a 60 Hz panel, so only the newest
  frame per refresh is drawn. Present-interval p99 gaps of 83–100 ms match the gaps
  in the source capture (idle moments in the clip), not dropped frames.
- Visual check (text sharpness, colour) was not reported with the numbers.

## Known issues
- `app-win/build.rs` copies the FFmpeg DLLs next to `glass.exe` locally but not
  on the CI runner. CI puts `third_party/ffmpeg/bin` on `PATH` instead. Cause not
  found yet.
- NVENC's RGB input gives a BT.601 limited-range stream (FFmpeg forces the VUI).
  The client follows the stream's matrix, so colours are consistent. A BT.709
  conversion of our own can come later if needed.
- Resolution changes mid-recording are skipped (LATER(M7)). The mouse cursor
  isn't captured (LATER(M3)).
- Mac decode is synchronous and allocates CF objects per frame (LATER(M5)).
- Build locally with the MSVC toolchain inside a VS environment (`vcvars64`).
  The GNU toolchain can't link FFmpeg's `.lib` files.
