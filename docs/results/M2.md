# M2 — Live stream (unencrypted, LAN): results

**Status: DONE.** Live PC → Mac measured with test build `m2-test1` (78.8 s session).
**Date:** 2026-11-20

## What works
- **Protocol v1** (`docs/protocol.md`, ADR 0003): TCP control (Hello/Welcome,
  ping/pong clock sync, keyframe requests, Bye), UDP punch, 1400-byte video
  datagrams with the M0 header, per-frame info (`encode_us`, `frame_len`) in
  packet 0.
- **core**: packetiser and reassembler (any order, duplicates, loss → withhold
  until IDR), min-RTT clock sync, host session, viewer client (receive +
  control threads, SPSC frame queue), replay host. 41 Rust tests, including a
  bit-exact loopback stream, keyframe-request restart and reconnect.
- **Windows host** (`glass host`, `host.cmd`): WGC → NVENC → UDP, IDR on
  connect and on request, re-sends the last frame as an IDR when the screen is
  idle. Prints and logs a per-session report.
- **`glass probe`** (headless viewer) and **`glass serve`** (replay). CI runs
  serve → probe over loopback on Windows and checks every frame is bit-exact.
- **Mac viewer**: connect window (remembers the address), full screen by
  default (⌃⌘F window, ⌘⇧S stats, ⌘W disconnect), aspect-fit with bars,
  hardware decode on its own thread, newest frame presented each refresh,
  stats overlay (2 s window) and a results window per session. XCTests stream
  both fixtures from core's replay host over loopback and decode them.

## Measured — Windows host, loopback (dev PC, RTX 4070, 2560×1440 @ 165 Hz, 8 s)

`glass host --local` → `glass probe 127.0.0.1` on the same PC, normal desktop
activity (~64 fps of changed frames). Network numbers here are loopback, not LAN.

| | p50 | p99 | max |
|---|---|---|---|
| encode (capture → encoded) | 5.26 ms | 17.17 ms | 25.07 ms |
| send (packetise + `send_to`, per frame) | 1.54 ms | 5.22 ms | 6.22 ms |
| network (encoded → last packet at viewer) | 1.60 ms | 5.26 ms | 6.26 ms |
| capture → last packet at viewer | 7.00 ms | 21.09 ms | 28.39 ms |

509 frames, 0 lost, clock offset −5 µs (same clock both ends; RTT 0.3 ms).
A second 8 s run with a quieter screen: encode p50 5.52 / p99 11.88 ms, send
p50 0.64 ms, 0 lost.

**Hot-path before/after (encode).** `glass record` (M1 path, no network) right
before the host run, same screen activity: encode p50 5.02 / p99 11.53 ms at
64 fps. The host's p50 is within 0.25 ms of that. Its extra GPU copy (last
frame kept for idle IDRs) doesn't show at p50; p99 is noisier between runs.
Both are slower than M1's busy-screen run (p50 2.43 ms at 125 fps), the same
"sparse frames → GPU clocks down" effect noted in M1.

**Send cost is the surprise:** about 75 µs per `send_to` on Windows loopback,
or ~1.5 ms per 55 KB frame, and an IDR (~150 datagrams) would take ~11 ms.
This is on the capture/encode thread, so it adds directly to latency. It still
needs measuring on a real NIC. If it holds there, M5 should batch sends
(Windows UDP send offload, `UDP_SEND_MSG_SIZE`) or move sending to its own thread.

## Measured — PC → Mac over the LAN (m2-test1)

PC: RTX 4070, 2560×1440 @ 165 Hz, HEVC 4:2:0 at 80 Mbps cap, on Wi-Fi.
Mac: MacBook Air M4 (Mac16,12), macOS 27.2.1, built-in 2940×1912 @ 60 Hz,
full screen. Same Wi-Fi network; clock-sync RTT 4.1–5.2 ms suggests the Mac
was on Wi-Fi too. Normal desktop use for 78.8 s.

| Stage | p50 | p99 | max | notes |
|---|---|---|---|---|
| encode (host) | 2.88 ms | 10.50 ms | 207 ms | max is a single outlier |
| send (host, packetise + `send_to`) | 0.67 ms | 5.69 ms | 8.67 ms | ~22 µs per datagram on the real NIC, vs ~75 µs on loopback |
| network (encoded → last packet at Mac) | 5.60 ms | 12.54 ms | 110 ms | includes send; clock error ±2 ms |
| queue (last packet → decode) | 0.02 ms | 1.75 ms | 11.3 ms | |
| decode | 2.02 ms | 2.92 ms | 4.72 ms | hardware |
| wait for refresh (decoded → display link) | 4.49 ms | 20.47 ms | 32.0 ms | |
| **present (submit → on screen)** | **32.43 ms** | 48.99 ms | 49.3 ms | ≈ 2 refreshes at 60 Hz |
| **capture → screen** | **48.12 ms** | **71.70 ms** | 123 ms | n = 2984 |
| present interval | 16.67 ms | 116.67 ms | 900 ms | gaps match idle capture (host capture-interval p99 47.8 ms, max 895 ms) |

- **Traffic:** 6036 frames sent (76.7 fps of changed frames), 23.6 Mbps avg,
  frame p50 41.7 KB, max 379 KB. All 168,800 packets arrived: **0 lost frames**.
- **Recoveries:** "queue full" happened twice (24 frames withheld until the
  next IDR, 4 keyframe requests, 8 IDRs sent incl. 1 idle re-send). Decode
  never exceeded 4.7 ms, so the cause is bursts: Wi-Fi held packets for up to
  110 ms, then delivered more than the 8-frame queue holds at once.
- **Shown:** 2984 frames at 37.8 fps on the 60 Hz panel; 3023 decoded frames
  were superseded by a newer one before the next refresh (expected at 77 fps in).

- **Felt (user):** "ever so slightly jittery". It fits the numbers. The PC
  sends changed frames at up to 165 Hz, but the Mac shows the newest one on
  each 60 Hz refresh, so motion advances by an uneven 2 or 3 capture steps per
  refresh (rate-mismatch judder). Frames that miss a refresh show up as
  wait-for-refresh p99 20 ms. Wi-Fi bursts add to it. This is M5's
  smoothness work (jitter buffer, display-linked pacing, host capture rate
  matched to the viewer's refresh). Compare M5 against these numbers.

### Where the 48 ms goes
p50: encode 2.9 + network 5.6 + decode 2.0 + wait 4.5 + **present 32.4** ≈ 47.4 ms.
Two thirds is `CAMetalLayer` queueing (submit → photons ≈ 2 frames at 60 Hz),
the same 27–29 ms seen in M1. That's M5's main target: present just ahead of
vsync with `maximumDrawableCount = 2` (or `displaySyncEnabled = false`),
driven by core's jitter buffer. Without it, the SPEC target of 8–15 ms
can't be reached on this display. Next is the network (Wi-Fi). A wired run
would show how much of the 5.6 ms (and the 110 ms bursts) is Wi-Fi.

## CI (macOS VM, Apple M1 Virtual)
The packaged `Glass.app` connects to `glass serve` (320×192 fixture) over
loopback: frames decode in hardware, 0 lost, network p50 0.25 ms. The VM
reports no presented times (no real display), and VideoToolbox stalls of
200–575 ms near the start fill the 8-frame queue. The viewer then drops, asks
for a keyframe and recovers by itself (6–8 requests in 6 s). On the real Mac,
watch the "queue full" and "keyframe requests" counts.

## Known issues
- No FEC (M4): any lost packet costs a frame plus a keyframe round trip.
- The 8-frame receive queue overflows on Wi-Fi bursts (2× in 79 s); M5's
  jitter buffer should drop to the newest decodable frame instead.
- Windows Firewall: dismissing the first-run prompt creates Block rules for
  that glass.exe, and the Mac then can't connect ("can't find the PC" in the
  first try). Each test build unzips to a new path and asks again.
- No pacing of datagram bursts; IPv4 only; one viewer at a time.
- Mac viewer queues 1–2 refreshes in `CAMetalLayer` (seen in M1); M5.
- Cursor not shown (M3). Resolution changes on the host end the picture until
  the next session (M7).
- Clock-sync error is up to ±RTT/2 (shown in the report).
