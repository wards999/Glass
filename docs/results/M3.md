# M3 — Input: results

**Status: DONE.** Both test builds measured on the real PC and Mac over home Wi-Fi.
**Date:** 2026-11-20 · builds `m3-test1`, `m3-test2`

## What works
- **Protocol v2/v3** (`docs/protocol.md`, ADR 0004): loss-tolerant input
  datagrams (recent events repeated, state reconciled), pointer shape and
  visibility over TCP, `input_seq` in each frame for input → screen, and (v3)
  `HostNotice` when Windows is blocking input.
- **core**: `InputSender`/`InputApplier`, key tables (Mac kVK → HID → Windows
  scan code, Mac-/PC-style modifiers, ISO keyboards). 54 Rust tests, including
  2000 key events through 20% random loss with nothing left stuck and ≥ 99%
  delivered exactly once.
- **Windows host**: `SendInput` injection on the UDP thread, pointer shape
  capture, release-all at session end; (test 2) detection of admin windows and
  the secure desktop, QuickEdit turned off in the host console.
- **Mac viewer**: pointer, buttons, precise scrolling, keys (local monitor,
  ⌘ keyUp workaround, Caps Lock), PC pointer as the Mac cursor, ⌃⌥⌘ chords,
  PC-style modifier toggle, input → screen in the overlay and results.

## Measured — m3-test1 (153 s, home Wi-Fi, PC 2560×1440 @ 165 Hz, MacBook Air M4 @ 60 Hz)

Input (host side): 6990 datagrams (Mac sent 6989), 57 keys, 47 clicks, 274
scrolls, 2735 pointer moves, **0 repairs** (no event ever needed the state
backstop). Mac keyboard detected as ISO, Mac-style modifiers.

| Stage | p50 | p99 | max |
|---|---|---|---|
| encode (host) | 3.19 ms | 17.79 ms | 35.9 ms |
| send (host) | 0.31 ms | 1.61 ms | 3.0 ms |
| network (Wi-Fi) | 4.89 ms | 9.26 ms | 53.9 ms |
| decode | 2.21 ms | 3.73 ms | 4.3 ms |
| wait for refresh | 5.95 ms | 19.69 ms | 33.5 ms |
| present (display queue) | 32.23 ms | 49.09 ms | 49.3 ms |
| **capture → screen** | **50.41 ms** | **73.86 ms** | 101 ms |
| input → screen (as measured, see below) | 65.83 ms | 199.28 ms | 483 ms |

7148 frames received, 0 lost, 4 skipped after 1 queue overflow (2 keyframe
requests), 17.3 Mbps average, clock-sync RTT 3.8–4.1 ms.

- **Wi-Fi was better than in M2:** network p99 9.3 ms (M2: 12.5), max 54 ms
  (M2: 110).
- **Capture → screen is unchanged from M2 (50 ms)**, and the display queue
  (32 ms) is still two thirds of it: M5.
- **input → screen was over-reported in test 1.** Pointer moves (2735 of the
  input) advanced `input_seq`, but the pointer isn't in the captured picture,
  so a move produces no frame and got timed against whatever changed next.
  The idle gaps (capture interval p99 422 ms) then showed up as the p99/max.
  Fixed in test 2: only key, click, scroll events and repairs count. Even
  then it includes the app's own reaction time, so it's an upper bound on
  Glass's share.
- Encode p99 18 ms again with sparse frames (47 fps): GPU clocks dropping
  between frames, as in M1. M5.

Input: 4933 datagrams, 18 clicks, 1237 scroll events, 1754 moves, 0 keys this
session, **0 repairs**; Windows blocked nothing (no admin window or UAC prompt
was hit, so the new warning wasn't exercised).

| network (Wi-Fi) | 4.93 ms | 10.27 ms | 40.4 ms |

7360 frames (84 fps), 0 lost, 0 skipped, 0 queue overflows, 0 keyframe

- **The corrected input → screen now agrees with capture → screen**
  (49 vs 47 ms p50): input reaches the PC in about 2–3 ms, and the rest is the
  same video path, dominated again by the Mac's display queue (32 ms).
  Against SPEC §0 B (≤ 35 ms p50) that is 14 ms short, and M5 is where it's
  won.
- The cleanest session so far: no loss, no recoveries, encode p99 9.3 ms.

## Problems found in test 1 (fixed in test 2)
1. **Couldn't quit while viewing:** ⌘Q goes to the PC. Now ⌃⌥⌘Q.
2. **Clicks stopped working (pointer still moved) after clicking into the
   host.cmd window.** The pointer is drawn on the Mac, so it always "moves".
   The two causes Windows doesn't report are an administrator window in front
   (UIPI) and the secure desktop (UAC prompt, lock screen). `SendInput`
   returns success for both, so test 1's "blocked by Windows 0" couldn't see
   it. Test 2 detects both, prints them in the host window, counts the input
   lost to them, and shows a warning on the Mac. It also turns off the host
   console's QuickEdit mode: clicking in that window could otherwise pause
   the host at its next message. Root cause still to be confirmed by test 2.

## Felt (user)
- The mouse stopped selecting things towards the end, starting when clicking
  into the host.cmd window (above).
- Test 2: "all good". Clicking into the host.cmd window no longer breaks
  input, and pointer, clicks and scrolling felt right.
- Not exercised by the user: the admin-window / UAC warning (no blocking
  happened in test 2). The detection is covered only by a unit test on the
  normal desktop; confirm it the next time an admin window is in front.

## Known issues
- macOS keeps ⌘Tab, ⌘Space and Mission Control; no relative mouse mode (M5b).
- Keys are physical; both machines need the same keyboard layout.
- Elevated windows need an elevated host; the secure desktop can't be reached.
