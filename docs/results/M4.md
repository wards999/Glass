# M4 — Robustness on Wi-Fi

**Status: in progress.** Steps in ADR 0020. Step 1, FEC, is built (protocol
v10, m4-test1).

## Step 1: FEC

Reed–Solomon parity per frame, in interleaved groups of up to 64 data packets,
sized from the loss the viewer reports.

### losssim (`cargo run -p losssim --release -- --check`)

6000 frames at 60 fps (a keyframe every 2 s, the rest 2–31 packets), the real
packetiser, FEC and reassembler, a little reordering. FEC follows the loss
the receiver reports.

| loss | seen | frames lost | rebuilt | FEC extra (packets) |
|---|---|---|---|---|
| random 0% | 0.00% | 0 (0.00%) | 301 | 14.3% |
| random 1% | 0.99% | 0 (0.00%) | 1311 | 26.5% |
| random 2% | 1.96% | 0 (0.00%) | 2331 | 33.2% |
| **random 5%** | 4.99% | **0 (0.00%)** | 5445 | 51.2% |
| random 10% | 9.80% | 4 (0.07%) | 10559 | 74.8% |
| bursts 1.1% (runs ~4) | 0.96% | 29 (0.48%) | 1175 | 28.5% |
| bursts 3.9% (runs ~7) | 3.84% | 88 (1.47%) | 3706 | 50.4% |

- 5% random loss loses no frame, as CLAUDE.md requires (`--check`).
- First version: parity as a percentage of the data. 5% random loss then
  still lost 0.32% of frames, because tiny frames (2–3 packets) got 1 parity
  packet. Parity is now sized by probability: at most a 1-in-10 000 chance a
  group fails at the reported loss. Tiny frames get relatively more.
- Reordered packets were first counted as lost, so a clean link "saw" 0.26%
  loss. They no longer count, and no longer slow file copies as "late".
- Bursts long enough to take out a small frame need NACK (step 2).
- The FEC extra is in packets; tiny frames make it look bigger than the
  bytes it costs.

### m4-test1 on the real machines: the session dropped during a YouTube video
- **Bug:** a reordered packet takes one back off the viewer's missing count.
  The next loss report then subtracted past zero and wrapped: the viewer
  reported 100 % loss, and the host doubled the video with parity and
  flooded the Wi-Fi.
- **Fixed in m4-test2:**
  - the reports saturate, and missing can never exceed expected;
  - the host plans FEC for at most 15 % loss;
  - parity per group is capped at half again (3 for tiny frames).

  Past that the link is full, and more parity only fills it further.
  Congestion is M5's job.
- Glass.exe also disappeared from QUIETPC22's folder afterwards: Windows
  Defender removed it as "severe" (unsigned, ADR 0008). The user restored it.

A 1.3 GB copy to QUIETPC took 17 min (~1.3 MB/s) in the same build. The
file-speed rule from m5c-test10 halved on any single frame 5 ms over the

steers by the average frame instead (ADR 0016).

## Step 2: NACK (m4-test6, ADR 0021)

losssim, now with a 4 ms round trip, NACKs and resends that can be lost
too, and 6000 frames at 60 fps per scenario:

| loss | seen | FEC extra | lost, FEC only | lost, with NACK | NACKs | resent | late p99 / max |
|---|---|---|---|---|---|---|---|
| random 0% | 0.00% | 14.3% | 0 | 0 | 0 | 0 | 0 / 0 ms |
| random 1% | 0.99% | 26.4% | 0 | 0 | 0 | 0 | 0 / 0 ms |
| random 2% | 1.94% | 32.5% | 0 | 0 | 0 | 0 | 0 / 0 ms |
| **random 5%** | 5.05% | 46.8% | **0** | **0** | 0 | 0 | 0 / 0 ms |
| random 10% | 9.86% | 51.7% | 4 (0.07%) | 2 (0.03%) | 2 | 2 | 0 / 8.0 ms |
| bursts 1.1% (runs ~4) | 0.96% | 28.5% | 23 (0.38%) | **0** | 14 | 31 | 0 / 8.1 ms |

"Late" is how much later than on time frames reached the decoder: only
frames behind a recovered one wait, a round trip or two.

### m4-test6 (QUIETPC22 viewing the MacBook Air, Wi-Fi, a 1.37 GB paste)

| | |
|---|---|
| length | 133 s, 6116 frames, 0 lost, 2 keyframe requests |
| NACK | 6 asks, 0 resent packets used, 77 duplicates |
| network | p50 3.26 ms, p99 11.55 ms, max 39 ms (during the copy) |
| capture → screen | p50 19.12 ms, p99 31.05 ms |
| **file copy** | **1374.6 MB in 44.5 s: 30.9 MB/s** (speed set 5.7–60 MB/s) |

- The copy is fixed: 30.9 MB/s against about 8 MB/s for Remote Desktop
  (1 GB in 2 min 7 s), and the picture lost no frame meanwhile.
- No packet was really lost. The 6 NACKs were for packets that were only
  late (Wi-Fi was busy with the copy). The originals came first, the
  resends were duplicates. That cost about 100 KB, no delay. The results
  still said "5 frames saved". Since m4-test7 a frame counts as saved only
  if a resent packet completed it.

## Step 3: recovery (m4-test10, ADR 0022)

- FFmpeg's hevc_nvenc has no reference invalidation (only intra refresh,
  which leaves damage on screen), so a lost frame still needs a keyframe.
- No more IDR every 10 s on Windows: on the RTX 4070, 30 s at 60 fps gave
  1 keyframe (was 3).
- The viewer now reports the hitch after a loss. Numbers to come.

## Step 4: the network (m4-test11, ADR 0023)

- Video marked as video and input as voice: qWAVE on Windows,
  SO_NET_SERVICE_TYPE plus IP_TOS on the Mac. The results say whether the
  OS accepted it.
- Windows advertises its Ethernet or Wi-Fi address, chosen by adapter kind
  and gateway: 192.168.4.43 on QUIETPC22.
- A keep-awake every 10 ms when nothing else is sent, each way.
- MTU probe deferred.
- Numbers to come.

## Step 5: Wi-Fi spikes and the link (m4-test12, ADR 0024)

- Spikes (first-packet time 8 ms over typical) are counted and
  classified by their period: AWDL about 1 s, a scan about 60 s, power
  save 0.1–0.5 s, or irregular. Unit tests cover each pattern on synthetic
  traces.
- "Wi-Fi here" on both ends: QUIETPC22 reads −42 dBm, 92 %, 1729 Mbps,
  channel 85.
- Numbers from real sessions to come.
