# M4 — Robustness on Wi-Fi

**Status: in progress.** Steps in ADR 0020. Step 1, FEC, is built (protocol
v10, m4-test1).

## Step 1: FEC

Reed–Solomon parity per frame, in interleaved groups of up to 64 data packets,
sized from the loss the viewer reports.

### losssim (`cargo run -p losssim --release -- --check`)

6000 frames at 60 fps (a keyframe every 2 s, the rest 2–31 packets), the real
packetiser, FEC and reassembler, a little reordering. FEC follows the loss
the receiver reports.

| loss | seen | frames lost | rebuilt | FEC extra (packets) |
|---|---|---|---|---|
| random 0% | 0.00% | 0 (0.00%) | 301 | 14.3% |
| random 1% | 0.99% | 0 (0.00%) | 1311 | 26.5% |
| random 2% | 1.96% | 0 (0.00%) | 2331 | 33.2% |
| **random 5%** | 4.99% | **0 (0.00%)** | 5445 | 51.2% |
| random 10% | 9.80% | 4 (0.07%) | 10559 | 74.8% |
| bursts 1.1% (runs ~4) | 0.96% | 29 (0.48%) | 1175 | 28.5% |
| bursts 3.9% (runs ~7) | 3.84% | 88 (1.47%) | 3706 | 50.4% |

- 5% random loss loses no frame, as CLAUDE.md requires (`--check`).
- First version: parity as a percentage of the data. 5% random loss then
  still lost 0.32% of frames, because tiny frames (2–3 packets) got 1 parity
  packet. Parity is now sized by probability: at most a 1-in-10 000 chance a
  group fails at the reported loss. Tiny frames get relatively more.
- Reordered packets were first counted as lost, so a clean link "saw" 0.26%
  loss. They no longer count, and no longer slow file copies as "late".
- Bursts long enough to take out a small frame need NACK (step 2).
- The FEC extra is in packets; tiny frames make it look bigger than the
  bytes it costs.

### m4-test1 on the real machines: the session dropped during a YouTube video
- **Bug:** a reordered packet takes one back off the viewer's missing count.
  The next loss report then subtracted past zero and wrapped: the viewer
  reported 100 % loss, and the host doubled the video with parity and
  flooded the Wi-Fi.
- **Fixed in m4-test2:**
  - the reports saturate, and missing can never exceed expected;
  - the host plans FEC for at most 15 % loss;
  - parity per group is capped at half again (3 for tiny frames).

  Past that the link is full, and more parity only fills it further.
  Congestion is M5's job.
- Glass.exe also disappeared from QUIETPC22's folder afterwards: Windows
  Defender removed it as "severe" (unsigned, ADR 0008). The user restored it.

| session switch (viewer kept) | picture paused 247 ms |

The YouTube drop is fixed: the session ran to the end, and the loss
report stayed sane (0.00 %), so parity stayed at its floor.

A 1.3 GB copy to QUIETPC took 17 min (~1.3 MB/s) in the same build. The
file-speed rule from m5c-test10 halved on any single frame 5 ms over the
baseline, routine on Wi-Fi, so it sat near the 1 MB/s floor. m4-test4
steers by the average frame instead (ADR 0016).

## m4-test4 (same machines, a file pasted on QUIETPC)

119 s, 0 lost frames, network p50 2.93 ms, p99 12.83 ms (10.50 without a
copy), max 32 ms, capture → screen p50 16.69 ms, p99 30.43 ms. One frame
took 157 ms (encode 139 ms on the host), probably as the paste started. The
report showed no copy speed, so m4-test5 adds a "file data" part to the
clipboard line on both sides: bytes each way, the time copies moved, the
average speed and the lowest and highest speed set.
