# M6 — Security: results

**Status: DONE.** m6-test1 passed on the real PC and Mac (2026-11-20).
**Date:** 2026-11-20 · design: ADR 0010 · protocol v4

## What's in it
- **Pairing:** 6-digit PIN shown on the host, typed on the viewer, run as
  SPAKE2 tied to both certificate fingerprints and the TLS session.
  Limits: 3 wrong tries per PIN, 10 per host run, then pairing is off until
  the host restarts.
- **Every connection:**
  - Mutual TLS 1.3, each side checking the other's pinned fingerprint.
  - The viewer refuses an unknown host before sending anything.
  - The host gives an unknown viewer no session.
- **Every UDP datagram** (video, input, punches):
  - AES-128-GCM with per-session, per-direction keys from the TLS exporter.
  - Counter nonces, a key ratchet every 2^23 packets, and a 1024-packet
    replay window.
- **Windows host:**
  - The key is DPAPI-encrypted in `%APPDATA%\Glass`.
  - host.cmd shows PINs, refusals and who's connected.
  - `--ask`, `glass devices`, `glass forget`.
  - Listed on the network as `_glass._tcp`.
- **Mac viewer:**
  - Lists Glass PCs on the network and asks to pair, with a PIN sheet.
  - Connection ▸ Paired Devices ▸ Forget.
  - Identity stored in a 0600 file in `~/Library/Application Support/Glass`.

## Measured here (Windows PC, loopback)
- **Core tests:** 76 pass (5 runs in a row). The new tests cover:
  - right and wrong PIN, the lockout after 10, and a cancelled pairing
  - a MITM with its own certificate, and a MITM across two TLS sessions
  - a different host at the same address
  - a forgotten device (refused, no input applied)
  - the "ask" deny and allow
  - forged plaintext and junk UDP while a session runs (ignored)
  - tampering with any byte, the wrong key or session
  - replay and reordering inside and outside the window
  - nonce uniqueness, key rollover, and catching up after a long loss
  - pairing and connecting over the C ABI, and DPAPI round-trip.
- **Encryption cost:** seal + open of one 1400-byte datagram takes
  **308 ns** (~4.5 GB/s, release build). A 1440p IDR is about 150
  datagrams, so ≈ 23 µs on the host per IDR. That is invisible next to
  `send` p50 0.31 ms.
- **`glass serve` ↔ `glass probe`, real binaries:**
  - Unpaired probe: refused.
  - Wrong PIN: refused, and the host said "2 more tries".
  - Right PIN: paired and streamed 131 frames, 0 lost, 0 rejected.
  - Reconnect without a PIN: 86/86 frames bit-exact.
  - `glass devices` listed the probe. After `glass forget` it was refused again.
  - The key file on disk is a DPAPI blob, not the plain key.

## Checked on the real PC and Mac — m6-test1
All five passed:
1. The PC was listed on the Mac automatically (mDNS).
2. A wrong PIN showed "Wrong PIN" with Try Again, and the PC said 2 more tries.
3. Reconnecting needed no PIN and the list showed "✓ paired".
4. After `glass forget` on the PC, the Mac had to pair again.
5. Paired Devices ▸ Forget on the Mac worked.

**Open problem (not M6):** once Task Manager, running as administrator, came
to the front, the viewer lost mouse control for the rest of the session.
UIPI drops all injected input while an elevated window has focus, so there
is no way to click away from it. m3-test2 only *detects* this. The fix is
for the host to run elevated (or, for UAC and the lock screen, as a
service). It is listed for the next step.

## Not compiled or tested here
- The Mac app (Swift: pairing sheets, Bonjour list, Paired Devices menu) is
  only built and tested in CI on macOS.
- mDNS listing between the real PC and Mac: needs `m6-test1`.

## Measured — m6-test1 (94 s, home Wi-Fi, PC 2560×1440 @ 165 Hz, MacBook Air M4 @ 60 Hz)

Paired and encrypted end to end: 191 859 sealed packets, **0 bad, 0
rejected, 0 lost frames**, 0 keyframe requests. 6780 frames (72 fps), 21.7
Mbps, RTT 3.6–4.7 ms. Input: 978 events in 5293 sealed packets, including
keys this time. The PC reported "input blocked by an admin window" once.

| Stage | m3-test2 p50 / p99 | m6-test1 p50 / p99 |
|---|---|---|
| encode (host) | 2.59 / 9.30 ms | 2.91 / 15.32 ms |
| network (Wi-Fi) | 4.93 / 10.27 ms | 5.26 / 10.46 ms |
| decode | 2.10 / 3.31 ms | 1.98 / 3.15 ms |
| wait for refresh | 4.63 / 17.00 ms | 4.72 / 17.50 ms |
| present (display queue) | 32.00 / 44.26 ms | 32.00 / 48.71 ms |
| **capture → screen** | **47.29 / 65.96 ms** | **48.00 / 71.93 ms** |
| input → screen | 49.36 / 82.72 ms | 65.84 / 215.89 ms |

Host side (`host.cmd`): 6781 frames sent, 5 IDRs, frame size p50 40 KB / p99
71 KB, 0 rejected UDP datagrams. Input: 98 keys, 40 clicks, 702 scrolls,
2090 moves, 0 repairs. **631 actions were blocked over 22.3 s by Task Manager**
(running as administrator, in front). Send (packetise + seal) p50 0.78 ms / p99
5.70 ms, up from 0.31 / 5.12 ms in M3. Sealing a 40 KB frame should cost
about 10 µs, so most of that rise is something else. Check it in M5 with a
per-step split; it is about 1% of capture → screen.

Frame-interval jitter: present interval p50 16.67 ms (the Mac's 60 Hz),
present sd 2.32 ms. The p99 of 267 ms is idle gaps when nothing on the PC
changed.

- **Encryption costs nothing measurable.** Capture → screen is within 1 ms
  at p50, and every stage is inside the run-to-run Wi-Fi and GPU-clock spread.
  This matches the 0.3 µs per packet measured locally. The encode p99 rise
  is the sparse-frame GPU-clock effect seen in M1 and M3 (M5).
- **input → screen is higher, but not because of M6.** Input rides the same
  sealed path, costing microseconds. Two things differ from m3-test2:
  - This run had keystrokes (m3-test2 had 0 keys), and they include the
    app's own time to redraw.
  - Input was blocked by Task Manager (admin) for 22 s of the 94 s run. Blocked
    events change nothing on screen, so they get timed against the next
    change, which explains the p99 and max (616 ms).
  - M5 should exclude blocked periods and split keys from clicks and
    scrolls.
- An earlier 19.6 s idle run (0 input, 7.6 fps) showed encode p50 8.5 ms
  and capture → screen 56.7 ms, which is the same sparse-frame effect.
